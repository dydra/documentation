Chapter — MCP & score

Point a model at your graph.

Every Dydra repository answers the Model Context Protocol at its own endpoint. A language model connects there and asks in whichever notation suits the question — SPARQL, GraphQL, or score, a compact notation for shaped queries that a model can write without knowing your namespaces. This chapter shows how a client connects, what each notation is for, and how to explore a repository you have never seen before.

01
what it is

What this is

A model that has to query a graph faces three problems at once: it must know the query language, it must know your vocabulary, and it must know your schema. SPARQL recommendations solve the first and nothing the other two - a model asked to write SPARQL against an unfamiliar schema invents IRIs and guesses relationships.

The MCP endpoint answers all. It accepts three request notations, and it profers introspections tools to explore the repository's schema:

SPARQL

When the question is already a query. The full language, answered as SPARQL Results JSON or as a graph.

GraphQL

When the client already speaks it. A schema exposes the RDF classes and properties as a GraphQL response document.

Score

When the shape of the answer is uncertain and the vocabulary is unknown. Bare names resolve against the repository; the server says what it resolved them to. Tools permit incremental graph exploration

A request names its notation as a media type. The server dispatches on that and answers in the paired notation, saying which one it used — so a client never guesses, and never has to ask for a format.

Score is the notation to reach for when exploring. It is a shape, not a query: you say which type you want and which properties, and the server compiles it to SPARQL, runs it, and remembers it as a node in an exploration tree you can branch from, join, walk, and refine. At any point you can ask what SPARQL a shape compiled to.

02
connect

Connecting a client

The endpoint

One endpoint per repository, taking POST requests:

https://dydra.com/{account}/{repository}/mcp

Each request carries a bearer token; authorization is checked per request, and the repository is the one in the path. There is nothing to open and nothing to close.

There is no handshake

MCP is a stateless protocol. A request carries its own protocol version and client capabilities in _meta, and mirrors its method and target into headers so that proxies can route without reading the body:

POST /acme/org-data/mcp HTTP/1.1
Content-Type: application/json
Accept: application/json, text/event-stream
Authorization: Bearer <token>
MCP-Protocol-Version: 2026-07-28
MCP-Method: tools/call
MCP-Name: query

{ "jsonrpc": "2.0", "id": 1, "method": "tools/call",
  "params": {
    "name": "query",
    "arguments": { "mimeType": "application/sparql-query",
                   "text": "SELECT (COUNT(*) AS ?n) WHERE { ?s ?p ?o }" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "ExampleClient", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities": {} } } }

The server answers with a single JSON object, or with an event stream scoped to that one request, according to what the client accepts. Both are ordinary MCP; a client library will handle the choice for you.

Because the call is an ordinary HTTP request, the request parameters the SPARQL endpoint understands are understood here too — ?timeLimit=30, ?describeObjectDepth=2 and the rest, read by the same initialization step and in force for the call. Content negotiation among them: a response content type applies to the envelope, which is a different thing from the notation of the result inside it. Where a tool argument names the same setting, the argument wins.

Ask the server what it is

server/discover reports the protocol versions it serves, its capabilities, and a plain-language instructions paragraph describing the notations. Read that once rather than carrying the explanation in your own prompt.

{ "supportedVersions": ["2026-07-28", "2025-11-25", …],
  "capabilities": {
    "tools": {}, "resources": {}, "prompts": {},
    "extensions": {
      "org.datagraph.spocq/notation": {
        "requestMediaTypes": ["application/sparql-query", "application/sparql-update",
                              "application/score", "application/graphql"] } } },
  "instructions": "…how to query this repository in the three notations…" }

Older clients still work. A client that opens with initialize, as the 2025-11-25 revision required, is served under those rules — a session id is assigned and echoed, and ping is answered. New clients should not use that path; it is there so existing ones keep working while they migrate.

Two tools

tools/list is how a client finds them. It takes no arguments and returns the manifest — each tool with its description and its JSON Schema, which is what a model reads to know what to send:

{ "jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": { "_meta": { … } } }

→ { "tools": [
       { "name": "query",
         "description": "Run one query against the RDF repository. The mimeType argument names …",
         "inputSchema": { "type": "object",
                          "required": ["mimeType", "text"],
                          "properties": { "mimeType": { "type": "string", … },
                                          "text":     { "type": "string", … },
                                          "limit":    { "type": "integer", … }, … } } },
       { "name": "score", … },
       … ],
     "ttlMs": 300000, "cacheScope": "private" }

The list is the same for every request and comes back in a fixed order, so a client may cache it. What varies is the authorization you present, not the connection.

ToolArgumentsWhat it does
query mimeType, text, limit, variables, session, describeForm, describeObjectDepth, describeSubjectDepth One request in any notation. Stateless.
score op, body, session, node, strict The exploration language — nineteen operations over a session you hold a handle to.

Where the older tools went

Previous versions had one tool per engine. Each of those remains as a deprecated alias that forwards to the two above, so existing clients keep working; each is a call you can make directly instead:

WasNow
sparql_select, sparql_describequery with mimeType: application/sparql-query
sparql_updatequery with mimeType: application/sparql-update
graphql_query, graphql_mutatequery with mimeType: application/graphql
list_graphsthe resource rdf://graphs — or a "SELECT DISTINCT ?g" SPARQL query, if you want it as bindings
orch_survey, orch_profile, orch_select, orch_suggest, orch_accept, orch_history, orch_navigatescore with the matching op

An alias answers in the paired notation like any other call. For example, sparql_select returns SPARQL results as JSON on an embedded resource. block.

03
notations

The three notations

The mimeType argument names the notation of text. It also determines the notation of the answer — the pairing is automatic and total, and the server never guesses a notation from the text:

Request mimeTypeNotationResponse mimeType
application/sparql-querySPARQL — SELECT, ASKapplication/sparql-results+json
application/sparql-querySPARQL — CONSTRUCT, DESCRIBEtext/turtle
application/sparql-updateSPARQL updateapplication/sparql-results+json
application/scorea scoreapplication/score
application/graphqla GraphQL documentapplication/graphql-response+json

Where the answer says what it is

The result travels as an embedded resource carrying its own media type, and the pairing is repeated in _meta for a client that routes on metadata:

{ "resultType": "complete",
  "content": [
    { "type": "resource",
      "resource": { "uri": "rdf://acme/org-data/result/9f2c…",
                    "mimeType": "application/sparql-results+json",
                    "text": "{\"head\":{\"vars\":[\"name\"]},\"results\":{…}}" } } ],
  "structuredContent": { "head": { "vars": ["name"] }, "results": { "bindings": [] } },
  "isError": false,
  "_meta": {
    "org.datagraph.spocq/requestMediaType":  "application/sparql-query",
    "org.datagraph.spocq/responseMediaType": "application/sparql-results+json" } }

A JSON-valued answer — SPARQL results, a GraphQL document — also arrives parsed as structuredContent, so a client need not parse the text itself. Score and Turtle are just unstructured text notations.

The dataset — before you write any SPARQL

A repository loaded from quads keeps its data in named graphs, and the SPARQL default graph is not their union. A query that names no graph reads an empty graph and answers nothing — no error, no warning, no rows. Either name the graph, or select over the union:

SELECT ?name WHERE { GRAPH ?g { ?s foaf:name ?name } }
SELECT ?name FROM <urn:dydra:all> WHERE { ?s foaf:name ?name }

The score tool already reads the union, so a shape needs nothing from you, and the SPARQL that materialize emits carries the clause it was evaluated with. Keep that prologue if you run the query elsewhere: removing FROM <urn:dydra:all> is the likeliest reason a materialized query returns nothing when run by hand.

The same question, three ways

SPARQL — when the query is the point

{ "mimeType": "application/sparql-query",
  "text": "PREFIX foaf: <http://xmlns.com/foaf/0.1/>
           SELECT ?name ?mbox WHERE { ?s a foaf:Person ; foaf:name ?name ; foaf:mbox ?mbox }" }

Score — when the vocabulary is the problem

{ "mimeType": "application/score",
  "text": "{ @type: Person, @shape: [name, email], @options: { limit: 10 } }" }

Three bare names, none of them a real IRI. The server resolves each against the repository's own vocabulary and tells you what it chose.

GraphQL — when the client already speaks it

The schema is derived from the repository's own classes and properties. Queries and mutations both go in the same media type; a mutation's fields all run in one transaction, so either the whole mutation takes effect or none of it does:

{ "mimeType": "application/graphql",
  "text": "{ person { Name Email } }" }

{ "mimeType": "application/graphql",
  "text": "mutation { createPerson(Name: \"Dave Green\", Email: \"dave@acme.org\") { Name } }" }

A GraphQL fault is reported inside the response document, in its errors member — the call itself succeeded. Pass variables as the variables argument.

An update

Updates go in their own media type, and are acknowledged in the SPARQL results family:

{ "mimeType": "application/sparql-update",
  "text": "INSERT DATA { GRAPH <http://acme/org-data/people> {
             <http://acme/org-data/dave> foaf:name \"Dave Green\" } }" }

→ { "head": {}, "boolean": true }

Sending an update as a query is an error. The response tells you which media type to use.

Describing one resource

When the question is "what does the store hold about this thing", the query form is DESCRIBE. It pairs to Turtle, like any graph-producing query:

{ "mimeType": "application/sparql-query",
  "text": "DESCRIBE <http://acme/org-data/alice>" }

→ text/turtle
<http://acme/org-data/alice>
    a                foaf:Person ;
    foaf:name        "Alice Chen" ;
    foaf:mbox        "alice@acme.org" ;
    org:memberOf     <http://acme/org-data/engineering> .

What counts as the description is a concise bounded description, and the store offers three forms with a separate reach in each direction — how far to follow forward through the objects of a statement, and how far to follow back through its subjects:

SettingValuesMeaning
describeForm asymmetric · symmetric · inverse Follow outward only; outward and inward; or inward only. The full names are simple-concise-bounded-description and its -symmetric- and -inverse- variants.
describeSubjectDepthinteger How far to follow the resource forward, as the subject of a statement. 1 gives its own statements; 2 also gives the statements of the resources they name. 0 gives none of them — the description comes back empty.
describeObjectDepthinteger How far to follow it backward, as the object of a statement — what points at this resource, then what points at those.

These are repository and request configuration (urn:dydra:describeForm, urn:dydra:describeObjectDepth, urn:dydra:describeSubjectDepth). They reach a query by either of two routes.

As arguments of the call, beside mimeType and text:

{ "mimeType": "application/sparql-query",
  "text": "DESCRIBE <http://acme/org-data/alice>",
  "describeForm": "symmetric",
  "describeSubjectDepth": 2,
  "describeObjectDepth": 1 }

Or as parameters of the request that carries the call. An MCP call is an ordinary HTTP request, so the parameters the SPARQL endpoint understands are understood here too — see the HTTP API:

POST /acme/org-data/mcp?describeSubjectDepth=2&describeObjectDepth=1

The arguments of the call take precedence over the parameters of the request, and both over the repository's configured defaults. When none are given, the defaults stand.

From a question to an answer

The shortest honest path from a question in words to a result you can quote, for a client that would rather write SPARQL than explore:

1 · Read the vocabulary

{ "method": "resources/read",
  "params": { "uri": "rdf://acme/org-data/vocabulary" } }   ; Turtle: the real IRIs

2 · Write the query against what it says

{ "name": "query",
  "arguments": {
    "mimeType": "application/sparql-query",
    "text": "PREFIX foaf: <http://xmlns.com/foaf/0.1/>
             PREFIX org:  <http://www.w3.org/ns/org#>
             SELECT ?name ?org WHERE {
               ?p a foaf:Person ; foaf:name ?name ; org:memberOf ?o .
               ?o foaf:name ?org }",
    "limit": 50 } }

3 · Read the bindings

{ "head": { "vars": ["name", "org"] },
  "results": { "bindings": [
    { "name": { "type": "literal", "value": "Alice Chen" },
      "org":  { "type": "literal", "value": "Engineering" } },
    … ] } }

The same document arrives parsed as structuredContent. Answer from the bindings, and cite the IRIs the vocabulary gave you — not ones recalled from elsewhere.

04
score

Score notation

Score is JSON with four differences, each earning its keep for graph work. The name evokes a music score: a compact notation that prescribes the structure and lets the performer realize the rest.

A name is not a string

An identifier written without quotes is a name — it denotes a term, and can be mapped to an IRI. A quoted string is data. They are different things, and the notation keeps them apart:

{ foaf:name: Alice }     the value is the NAME Alice — a term to resolve
{ foaf:name: "Alice" }   the value is the STRING "Alice" — a data value

That distinction is what makes name resolution safe to apply everywhere: only names are candidates, so a literal is never rewritten into somebody's vocabulary.

Three kinds of name

  • QNames — foaf:name, org:memberOf. Written unquoted, expanded through the repository's prefix map.
  • Operators — @type, @shape, $eq. A fixed vocabulary, never resolved.
  • Bare names — Person, name. Resolved against the repository's vocabulary after parsing.

A full IRI is written in angle brackets — <http://example.com/ns#Type> — which is how you say a term the prefix map does not cover.

Shapes

@shape takes an array of property names, not an object. A plain name is a leaf property; a single-key object is a traversal into a sub-shape:

;; flat
{ @type: foaf:Person,
  @shape: [foaf:name, foaf:mbox],
  @options: { limit: 10 } }

;; one level down: each person's organizations, by name
{ @type: foaf:Person,
  @shape: [foaf:name, {org:memberOf: [foaf:name]}] }

;; a type the prefix map does not cover
{ @type: <http://example.com/ns#MyType>,
  @shape: [<http://example.com/ns#prop1>] }

Shape operators

OperatorTakesMeaning
@typea namethe class of the anchor entity
@shapearraythe properties to retrieve
@anchorobjectconstrain the anchor — { foaf:name: "Alice" } binds that property to a value
@optionalarrayproperties that need not be present
@unionarray of shapesalternatives
@orderarray[{field: foaf:name, dir: asc}], or a bare field name
@grouparraygrouping fields
@distincttrueduplicate elimination
@limitintegerrow cap; also @options: { limit: n }

Bare names, and what the server did with them

A shape written in bare names comes back with a record of the resolution, so a model can see the guess it was given and correct it:

{ @type: Person, @shape: [name, email] }

→ { node: n3, count: 10,
     results: [ … ],
     resolved:   { Person: foaf:Person, name: foaf:name, email: foaf:mbox },
     ambiguous:  { name: [foaf:name, schema:name] },
     unresolved: [] }

Where several terms share a local name, the most used wins and the alternatives are listed. Pass "strict": true on the tool call to make an ambiguous or unresolvable name an error instead of a guess.

Names are resolved by local part first, then by rdfs:label, both case-insensitively. A repository with labelled terms is markedly easier to explore in bare names than one without.

explore

Exploring a repository

The score tool takes an operation and a score-notation body. Nineteen operations, in six groups. Every one of them takes the session handle as "session", and every one that acts on a node takes an optional "node" — without it, the active node is used.

Session

OperationBodyWhat it does
connect—Open an exploration session and return its handle; populates the vocabulary cache from the repository.
disconnect—Close the session and release its tree.

Discovery

OperationBodyWhat it does
survey{ scope: types }Enumerate the repository's types, predicates, or graphs, with counts. { scope: predicates, for_type: foaf:Person } narrows to one type's predicates; { scope: graphs } lists named graphs.

Query

A cold start, end to end

An unfamiliar repository, from nothing to a query whose SPARQL you can read.

1 · Open a session

{ "name": "score", "arguments": { "op": "connect" } }

→ { session: "a1b2c3d4-…", repository: "acme/org-data",
     vocabulary: { types: 12, prefixes: 22 },
     expires_after_minutes: 30 }

Keep that handle. Every later call carries it as "session". It is checked against your credentials on each use, and expires after thirty minutes idle — a call against a stale handle says so and you open a new one.

The exploration itself is stored, as RDF in a repository of the account, so a handle resolves whichever server process receives it and survives that process being recycled. Nothing on the wire remembers the handle for you, but the tree behind it is not yours to keep.

Two clients on one handle are not serialized for you. If another client moves the exploration between your calls, your next operation is refused with a message saying it was not recorded. Read the current tree with history and apply the operation again.

2 · What is in here?

{ "name": "score", "arguments": { "op": "survey", "session": "a1b2c3d4-…" } }

→ { node: n1, scope: types, count: 12,
     results: [ { type: foaf:Person,       count: 847 },
                { type: org:Organization,  count: 23 },
                { type: foaf:Project,      count: 156 },
                … ] }

3 · What does a person look like?

{ "name": "score",
  "arguments": { "op": "profile", "session": "a1b2c3d4-…", "body": "foaf:Person" } }

→ { node: n2, type: foaf:Person, instance_count: 847,
     properties: [ { predicate: foaf:name,     count: 847, sample: "Alice Chen" },
                   { predicate: foaf:mbox,     count: 812, sample: "alice@acme.org" },
                   { predicate: org:memberOf,  count: 790, sample: org:Engineering },
                   … ] }

4 · Ask for a shape

{ "name": "score",
  "arguments": { "op": "select", "session": "a1b2c3d4-…",
                 "body": "{ @type: foaf:Person, @shape: [foaf:name, foaf:mbox], @options: { limit: 5 } }" } }

→ { node: n3, count: 5,
     results: [ { v1: "Alice Chen", v2: "alice@acme.org" },
                { v1: "Bob Park",   v2: "bob@acme.org" },
                … ] }

5 · Read the SPARQL it compiled to

{ "name": "score",
  "arguments": { "op": "materialize", "session": "a1b2c3d4-…", "body": "sparql" } }

→ { node: n4, format: sparql,
     query: "SELECT ?v1 ?v2 WHERE { ?s a foaf:Person ; foaf:name ?v1 ; foaf:mbox ?v2 } LIMIT 5" }

materialize is the audit path. Whatever a model composed, this says plainly what will run — check that it says what you meant before trusting the numbers.

6 · See where you have been

{ "name": "score", "arguments": { "op": "history", "session": "a1b2c3d4-…" } }

→ n1 survey     (complete, 12)
     └── n2 profile  (complete, 15)
         └── n3 select  (complete, 5)
             └── n4 materialize  (complete, 0) *

Asking for a next move

Two operations exist for a client that does not know what to do next — which is the ordinary condition of a model meeting a dataset for the first time.

suggest reads where you are — the active node's type, its shape, how many rows it returned, and which of the type's predicates you are not yet using — and proposes candidates from it. The mode says what kind of move you want:

{ "name": "score",
  "arguments": { "op": "suggest", "session": "a1b2c3d4-…", "body": "{ mode: expand }" } }

→ { node: n5, mode: expand,
     candidates: [
       { kind: expand, label: "Add org:memberOf",
         expression: { predicate: org:memberOf }, score: 0.5,
         rationale: "Add predicate org:memberOf to the shape" },
       { kind: expand, label: "Add foaf:title",
         expression: { predicate: foaf:title }, score: 0.5,
         rationale: "Add predicate foaf:title to the shape" },
       … ] }

Each candidate carries its kind — the operation it would run — its expression, a score to rank it by, and a rationale saying why. Nothing has run yet; a suggestion is a node in the tree like any other, and it holds its candidates.

accept runs one of them by index:

{ "name": "score",
  "arguments": { "op": "accept", "session": "a1b2c3d4-…", "body": "{ node: n5, candidate: 0 }" } }

→ { node: n6, count: 5, results: [ … ], accepted_from: n5 }

The result is whatever that operation returns, plus accepted_from: the tree records that this node came from a suggestion, and the suggestion records what was made of it. Omit node and the active node is used, which is what you want immediately after a suggest. Suggestion chains are depth-limited, so a client cannot loop by suggesting from a suggestion indefinitely.

Ordinary results carry advice too. A select that returns a great many rows comes back with a suggestions field proposing narrow; a survey proposes profiling its largest types. They are hints in the result, not nodes — suggest is the operation that ranks candidates you can accept.

06
compose

Composing explorations

Every operation leaves a node behind, and nodes combine. This is what the tree is for: two partial views of the same type become one, and a link between types becomes a traversal.

join — merge two views of one type

Two selects over foaf:Person, one with contact details and one with affiliation, become a single select over the union of their properties:

;; n5 — { @type: foaf:Person, @shape: [foaf:name, foaf:mbox] }
;; n6 — { @type: foaf:Person, @shape: [foaf:title, org:memberOf] }

{ "op": "join", "body": "{ node1: n5, node2: n6 }" }

→ { node: n7, count: …,
     results: [ { v1: "Alice", v2: "alice@acme.org",
                  v3: "Engineer", v4: org:Engineering }, … ] }

walk — follow a link to another type

A predicate whose objects are subjects elsewhere becomes a traversal. Give it a source and a predicate and the target type is discovered; give it two nodes and the linking predicate is found for you:

{ "op": "walk", "body": "{ source: n5, predicate: org:memberOf }" }

→ target type: org:Organization
   { node: n8, count: …, results: [ … ] }

The result is a nested shape — persons, each with the organizations they belong to:

{ @type: foaf:Person,
  @shape: [foaf:name, foaf:mbox,
           {org:memberOf: [foaf:name, org:hasSite]}] }

shape — adjust and re-run

A modifier is merged into a node's shape: @shape adds properties, @type replaces, @options override.

{ "op": "shape", "body": "{ node: n5, @shape: [foaf:age], @options: { limit: 20 } }" }

expand and narrow

expand adds one predicate to the active node's shape and re-evaluates — the quickest way to widen a result you have already got:

{ "op": "expand", "body": "org:memberOf" }

narrow records a constraint on the active node and re-evaluates it.

Note. narrow currently records the where clause and re-runs the parent query; the $-operator filters are not yet compiled into the query. To restrict a result today, put the constraint in the shape — @anchor binds a property to a value — or write the FILTER in SPARQL through query.

Aliases

Node ids are n1, n2, n3. Give the ones you will come back to a name, and use it anywhere an id is accepted:

{ "op": "name", "body": "{ node: n3, alias: people }" }

{ "op": "join", "body": "{ node1: people, node2: n6 }" }

Keeping a session

There is nothing to keep. The exploration is written to the account's own repository as it proceeds, as RDF — so there is no moment at which it is unsaved, and no operation that saves it. That is why the MCP surface has no save and no load: not an omission, but nothing left for them to do.

What remains is copying, and it is ordinary Graph Store Protocol work on an ordinary graph: GET the exploration's graph to take a copy elsewhere, PUT one to bring a copy in. Because the tree is stored as terms rather than as an encoded blob, it is also queryable alongside your data — which operations an account uses, which types were profiled and then abandoned, what a bare name resolved to and how often it was ambiguous.

A handle still expires after thirty minutes idle, and an expired exploration's graph is retained rather than reclaimed. Removing one is disconnect, or a DELETE on its graph.

07
context

What the server tells you

Beside the two tools, the endpoint serves the context needed to use them. These are generated from the repository itself, so they cannot drift from it — read them instead of describing your data in a system prompt.

Resources — things to read

A resource is a document at a URI. Two calls: resources/list to see what is there, resources/read to fetch one. Nothing is fetched implicitly; a client reads what it decides it needs.

1 · See what is available

{ "jsonrpc": "2.0", "id": 1, "method": "resources/list", "params": { "_meta": { … } } }

→ { "resources": [
       { "uri": "rdf://vocabulary", "name": "RDF Vocabulary",
         "mimeType": "text/turtle",
         "description": "RDF classes, properties, domain/range … Read this before writing SPARQL." },
       { "uri": "score://grammar", "name": "Score Grammar", … },
       … ],
     "ttlMs": 300000, "cacheScope": "private" }

A resource is named by what it is, not by where it lives. The endpoint is per-repository and the request already says which one, so the URI does not repeat it.

2 · Read the one you need

The URI goes in params.uri — and, because every request mirrors its target into a header, in MCP-Name as well:

POST /acme/org-data/mcp HTTP/1.1
MCP-Method: resources/read
MCP-Name: rdf://vocabulary

{ "jsonrpc": "2.0", "id": 2, "method": "resources/read",
  "params": { "uri": "rdf://vocabulary", "_meta": { … } } }

→ { "contents": [
       { "uri": "rdf://vocabulary",
         "mimeType": "text/turtle",
         "text": "@prefix foaf: <http://xmlns.com/foaf/0.1/> .\n
                  @prefix org:  <http://www.w3.org/ns/org#> .\n
                  foaf:Person a rdfs:Class .\n
                  foaf:name a rdf:Property ; rdfs:domain foaf:Person ; rdfs:range xsd:string .\n
                  org:memberOf a rdf:Property ; rdfs:domain foaf:Person ; rdfs:range org:Organization .\n…" } ],
     "ttlMs": 300000, "cacheScope": "private" }

3 · Put it to work

What you do with a resource depends on which it is:

ResourceTypeRead it when
rdf://vocabularyTurtle Before writing SPARQL or GraphQL. Place it in the model's context: it is the list of real classes, properties, domains, ranges and prefixes, and it is what stops a model inventing IRIs. On a large repository, read it once per conversation, not once per query.
rdf://typesJSON You want the classes present without the property detail — a cheap orientation, or a menu to offer a user.
rdf://graphsJSON You need to scope a query to a named graph, or to know how the data is partitioned.
score://grammartext Before writing score for the first time in a conversation. It is the notation, its operators, and worked examples — enough for a model that has never seen score to write a correct shape.
score://operationsscore Together with the grammar: the catalogue of §05 as data, with an example body for each operation. Generated from the same table the server dispatches on.
score://session/{handle}score You hold a session handle and want its tree without spending a tool call — the same content history returns, addressable by URI.

Every list and read carries ttlMs, a hint for how long the answer stays good, and cacheScope: "private" — what these hold depends on who asked, so no shared cache may keep them. A client may cache them for itself, and should: the vocabulary of a repository changes far more slowly than a conversation moves.

The longer form still works. Earlier releases advertised URIs that also named the repository — rdf://acme/org-data/vocabulary, score://acme/org-data/grammar. Those still resolve, and a read echoes back whichever form you asked for, so a client written against them needs no change. New clients should use the short form: keeping one repository's vocabulary apart from another's in a cache is the business of whoever keeps the cache, and not something the name has to carry.

Prompts — workflows to follow

A prompt is a ready-made instruction the server writes for its own surface, filled in with your repository and your question. A host application usually offers them to the user by name; a client can also fetch one directly and prepend it to the conversation.

1 · See what is offered

{ "method": "prompts/list", "params": { "_meta": { … } } }

→ { "prompts": [
       { "name": "explore-with-score",
         "description": "Explore the repository in score notation: survey, select, narrow or expand, then materialize the compiled SPARQL.",
         "arguments": [ { "name": "goal",
                          "description": "What you are trying to find out.", "required": false } ] },
       … ] }

2 · Fill one in

{ "method": "prompts/get",
  "params": { "name": "explore-with-score",
              "arguments": { "goal": "which teams has Alice worked with" },
              "_meta": { … } } }

→ { "description": "Explore in score notation",
     "messages": [
       { "role": "user",
         "content": { "type": "text",
                      "text": "Explore repository acme/org-data to: which teams has Alice worked with.\n
                               1. Read score://acme/org-data/grammar for the notation and
                                  score://acme/org-data/operations for the operations.\n
                               2. Call score with op=connect and keep the session handle …\n
                               3. op=survey to see the types, op=profile on a type …\n
                               4. op=select with a shape …\n
                               5. op=narrow or op=expand to refine, op=history to see the tree.\n
                               6. op=materialize to read the SPARQL your shape compiled to." } } ] }

3 · Use the messages

The messages array is ready to place in the conversation as it stands — role and content, in the shape a model expects. It is not executed and it is not a template to further fill in: the server has already written the whole instruction, naming this repository's own resource URIs. The three on offer:

PromptArgumentUse it to
explore-repositoryfocus Open a conversation about an unfamiliar repository: read the vocabulary, then query. Give focus a type or topic to steer it.
write-sparql-querydescription Get one SPARQL SELECT written and tested for a stated need, with the vocabulary read first.
explore-with-scoregoal Run the whole exploration loop — grammar, connect, survey, select, refine, materialize — for a stated goal.

A short recipe for a client with no prior knowledge of a repository: server/discover for the instructions, then resources/read on the vocabulary, then either write SPARQL or take explore-with-score from prompts/get and follow it. Three calls before the first question, and the model is working from the repository rather than from guesswork.

In practice

Two kinds of error, and only one is yours to fix

Anything a model could correct by trying again — a SPARQL syntax error, an unknown media type, a name that will not resolve, an expired session handle, or an exploration another client moved while you were working on it — comes back as a normal result flagged "isError": true, carrying an explanation to act on:

{ "resultType": "complete",
  "content": [ { "type": "text",
                 "text": "Unsupported request mimeType: application/x-nonesuch\n\n
                          Accepted request media types: application/sparql-query,
                          application/sparql-update, application/score, application/graphql." } ],
  "isError": true }

A JSON-RPC error means something else — an unknown method or tool, a malformed request, a header that disagrees with the body. Those are for the client's author, not for the model:

CodeHTTPCondition
-32700400The body is not JSON.
-32600200Not a JSON-RPC 2.0 message.
-32601404No such method. The JSON-RPC body is what tells you this is an MCP endpoint that lacks the method, rather than a server that is not one.
-32602400 / 200Invalid parameters — including an unknown tool, an unknown resource URI, and a request missing its required _meta.
-32603200An internal fault.
-32020400A required header is missing, or disagrees with the body.
-32022400Unsupported protocol version; data.supported lists the ones served.

Habits that pay

  • Read the vocabulary first. One resource read replaces a great deal of guessing, and it is the difference between a model that writes real IRIs and one that invents them.
  • Explore in score, deliver in SPARQL. Shape the question with the score tool, then materialize and keep the SPARQL. It runs anywhere and does not depend on a session.
  • Carry the session handle. It is an ordinary argument; nothing on the wire remembers it for you. Omitting it on a first call opens a session and hands you the handle in the result — take it from there.
  • Check what the names resolved to. Bare names are a convenience, not a guarantee. The resolved and ambiguous fields say what happened; strict turns a guess into an error where that matters.
  • Bound your queries. All three notations admit unbounded ones. limit on the tool call caps what comes back.

Other ways in

The exploration operations are not only reachable through MCP. The same functions answer at POST /orchestration/{account}/{repository}/{operation}, taking and returning score-notation bodies with a session field — a GET on any of those URLs describes the service. And from a Lisp image there is an interactive REPL:

(cli-orchestrator "acme/org-data"
                  :agent-name "user" :agent-key "token")

orch> connect
orch> survey
orch[n1]> profile foaf:Person
orch[n2]> select { @type: foaf:Person, @shape: [foaf:name] }
orch[n3]> tree

The CLI takes the same score bodies, prompts with the active node, and continues a line whose braces are unbalanced. It also has save and load against a file path — a convenience of working locally that the network surface does not offer.
