Getting started

This guides you along the shortest path from nothing to an answer: from an account, to a repository, then some statements in it, and eventually a query over them. It takes a few minutes. Everything here can be done in a browser or over HTTP, and both are shown, because most people start with the first and arrive at the second.

01
an account

An account

Accounts are created at https://dydra.com. The public service is free: create an account, make repositories, and query them at no cost.

An account name is the first segment of every URL you will use afterwards. A repository belonging to the account me and named foaf is addressed as https://dydra.com/me/foaf, and its SPARQL endpoint is that URL with /sparql on the end. Nothing else needs to be configured for this to be true.

02
authentication

Authentication

Reading a public repository needs no credentials. Everything else does, and there are three ways to present them.

A user name and password, by HTTP basic authentication. What the web interface uses when you sign in.

A token. Your account page carries an authentication token, which may be reset at any time – do that if it is ever exposed. A token is presented as an Authorization header with a bearer token:

Authorization: Bearer <token>

or, where signing a request is inconvenient, as basic authentication with the token as the user name and an empty password. Prefer a token to a password in anything you automate: it is scoped to the account, it can be rotated without changing a password, and it will not appear in a shell history if you keep it in the environment.

Neither, for a repository which permits anonymous access.

Note

Requests are made over https. A token in a URL query string can become a token in a proxy log; send it in a header.

03
a repository

A repository

In the web user interface, the account page has a New Repository button: a name is all that is required. Over HTTP, a repository is created by posting to the account’s repository collection:

$ curl -X POST https://dydra.com/system/accounts/me/repositories \
    -u '<token>:' \
    -H 'Content-Type: application/json' \
    -d '{"name": "foaf", "class": "lmdb-repository"}'

The body is a JSON object of repository settings. Two of them matter here: name, which is required, and class, which may be left out to take the default. The rest – summary, description, homepage, privacy, license – can be set now or edited later.

A repository’s class fixes what it can do, and cannot be changed afterwards:

Most classes are the ordinary quad store with something added, and the name says which:

revisioned-

keeps the history of every write, so a query may be addressed to a past revision.

annotated-

opens three triple-term permutation indices alongside the quad indices, which is what makes quoted triples – RDF 1.2, SPARQL 1.2 – queryable.

wide-

uses 24-byte index keys and 48-bit term numbers, for a repository that must address more distinct terms than a 32-bit term number allows.

They combine, and the concrete classes are the combinations that exist:

class

what it is for

lmdb-repository

the default: a six-way index over the quads

revisioned-lmdb-repository

the same, with history

annotated-lmdb-repository

quoted triples

annotated-revisioned-lmdb-repository

quoted triples, with history

wide-lmdb-repository

wide keys

wide-revisioned-lmdb-repository

wide keys, with history

wide-annotated-lmdb-repository

wide keys and quoted triples

wide-annotated-revisioned-lmdb-repository

all three

lmdb-replicable-repository

revisions identified rather than numbered, so that copies can agree

temporal-value-lmdb-repository

a valid-time index over the predicates you declare

hdt-repository

a read-only store backed by an HDT document

internal-view-repository

the materialised results of a view

Take the default unless you know you want one of the others. If you expect to ask what the data looked like last Tuesday, take the revisioned class now: history cannot be added to a repository after the fact.

The last four are for particular jobs rather than general use.

A replicable repository differs from a revisioned one in how a revision is named. A revisioned repository numbers its revisions with ordinals, which are private to the store, so two copies of the same data will not agree about them. A replicable repository identifies each revision instead, so a revision means the same thing wherever it is read – which is what lets one repository propagate its writes to another, at a replica location alongside the SPARQL endpoint, ending in replica.

A temporal-value repository indexes the valid time your data carries: the timestamps on predicates you have declared, indexed so that a time-bounded FILTER becomes a bounded index scan rather than a pass over the graph. This is the class the Temporal graphs and collated retrieval manual builds on, and that manual is the place to read about it.

Note

A class cannot be changed after the repository is created, and each of these costs something – space for the extra indices, write throughput for the revision records. Choose deliberately, and take lmdb-repository when nothing here applies.

04
statements in it

Statements in it

Data goes in through the Graph Store protocol. PUT replaces the repository’s contents, POST adds to them:

$ curl -X POST https://dydra.com/me/foaf/service \
    -u '<token>:' \
    -H 'Content-Type: text/turtle' \
    --data-binary @foaf.ttl

Turtle, N-Triples, N-Quads, TriG, RDF/XML and JSON-LD are all accepted; the Content-Type header says which one you are sending. A graph= query argument, or a Graph header, puts the statements in a named graph rather than the default one.

The web user interface does the same thing from its Import button, from a local file or from a URL it fetches for you.

Note

Upload content is limited to 128 MB per request. For a synchronous request that is the compressed size, so gzip the body and say Content-Encoding: gzip; for an asynchronous request it is the size of the data itself. Larger loads are made in several requests, or by pointing the service at a URL and letting it fetch.

05
an answer

An answer

The endpoint is standard SPARQL 1.1 Protocol, which means every SPARQL client already knows how to talk to it, and so does curl:

$ curl https://dydra.com/me/foaf/sparql \
    --data-urlencode 'query=SELECT (COUNT(*) AS ?n) WHERE { ?s ?p ?o }' \
    -H 'Accept: application/json'

[ { "n": 631 } ]

Accept chooses the response format: SPARQL Results in JSON or XML for SELECT and ASK, an RDF serialisation for CONSTRUCT and DESCRIBE. Update is the same endpoint with an update= parameter instead of query=.

In the browser, a repository page has a query editor, and a query worth keeping can be saved as a view – a named, parameterised query which is itself addressable.
