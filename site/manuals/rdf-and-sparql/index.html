RDF and SPARQL

Dydra stores RDF and answers SPARQL. Both are W3C standards, neither is ours, and that is the point: the data model and the query language are specified independently of any implementation, so what you write against Dydra you can read, move and re-run elsewhere. This manual is the short account of the two, for a reader who is about to use them rather than one studying them.

01
statements

Statements

RDF describes the world in statements, each one a subject, a predicate and an object. Nothing else. A statement asserts that some thing stands in some relation to some other thing:

<http://example.org/alice>  <http://xmlns.com/foaf/0.1/knows>  <http://example.org/bob> .
<http://example.org/alice>  <http://xmlns.com/foaf/0.1/name>   "Alice" .

The first names a relation between two things. The second attaches a value to one of them. A set of statements is a graph, and because every subject and predicate is an IRI – a globally unique name – two graphs written by two parties who never met can be put side by side and will agree about whatever they both name.

That is the whole model. There is no schema to declare first and migrate later, no table to widen, no column to add. A new kind of fact is a new predicate.

Terms

Three kinds of thing appear in a statement:

  • an IRI, naming something – a person, a document, a relation;

  • a literal, a value: a string, a number, a date. A literal carries a datatype ("631"^^xsd:integer) or a language tag ("Alice"@en);

  • a blank node, standing for something which exists but is not named.

Objects may be any of the three. Subjects may be IRIs or blank nodes. Predicates are always IRIs.

Serialisations

The model is one thing; writing it down is another. The same graph has many encodings, and Dydra reads and writes the ones in use:

  • N-Triples – one statement per line, as above. Verbose, and the easiest thing to generate and to stream.

  • Turtle – N-Triples with prefixes, abbreviation and nesting. What to write by hand.

  • N-Quads and TriG – the same two, extended with a fourth term naming the graph a statement belongs to.

  • RDF/XML and JSON-LD – for consumers which want XML or JSON.

Which media type carries which is a matter for the protocols; see Working over HTTP.

Named graphs

A repository holds more than one graph. Each statement may be attributed to a named graph, and a query may name the graphs it wants, so provenance, versioning by source, and per-graph access are all expressible without leaving the model. A statement plus its graph is a quad, which is why the serialisations come in pairs.

02
queries

Queries

SPARQL asks for the statements which match a pattern. A pattern is a statement with variables in it:

PREFIX foaf: <http://xmlns.com/foaf/0.1/>

SELECT ?name WHERE {
  ?person foaf:knows <http://example.org/bob> .
  ?person foaf:name  ?name .
}

Two patterns sharing a variable are a join; the engine finds every assignment that satisfies both. Where SQL joins tables you have declared, SPARQL joins statements you have merely asserted, which is the practical difference between the two languages.

Four query forms

  • SELECT returns a table of variable bindings.

  • CONSTRUCT returns a graph, built from a template.

  • ASK returns true or false.

  • DESCRIBE returns the statements around a term. Which statements exactly is deliberately left to the implementation; Dydra’s rule is configurable, and is described under describe form in the reference.

Beyond matching

SPARQL 1.1 is a good deal more than pattern matching, and Dydra implements the specification rather than a subset:

  • OPTIONAL, UNION, MINUS and FILTER for shaping a result;

  • GROUP BY with COUNT, SUM, AVG and the rest;

  • property paths, so “a friend of a friend, to any depth” is foaf:knows+ rather than a query per depth;

  • subqueries, VALUES, BIND, and a function library;

  • INSERT and DELETE – update is part of the language, so a repository is written with the same language it is read with;

  • SERVICE, which sends part of a query to another endpoint.

Results come back as SPARQL Results in XML or JSON for SELECT and ASK, and as any RDF serialisation for CONSTRUCT and DESCRIBE.

03
what dydra adds

What Dydra adds

Dydra is a standards implementation first: a query which runs here should run anywhere, and the extensions are additions rather than dialect.

Revisions. Every write produces a new repository state, and a query may be addressed to a past one. Transaction time is a property of the store rather than something you model in your data.

Valid time. A repository may index the timestamps your data carries, so a window over the time your facts are about is an index range rather than a scan. See the Temporal graphs and collated retrieval manual.

Views. A query may be saved, named, given parameters and called – and its results may be materialised into a repository of their own.

Federation. SERVICE against another Dydra repository or a remote endpoint, subject to authorization on both ends.

RDF 1.2, early. A pre-alpha of quoted triples, which allow a statement to be the subject or object of another statement – saying something about a statement without reifying it by hand.
