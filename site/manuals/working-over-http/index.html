Working over HTTP

Dydra is an HTTP service and nothing else: there is no driver to install and no wire protocol to learn. Everything a program does – create a repository, load statements, run a query, read a past revision – is a request to a URL, made with whatever HTTP client the language already has.

This manual is the tour. It says which endpoint does what, which parameters matter in practice, and where the exact specification of each lives in the API reference. Where the two disagree, the reference is right.

01
the endpoints

The endpoints

Every URL begins with the account name, and repositories hang directly off it. For the account me and the repository foaf:

URL

what it is

/me/foaf/sparql

SPARQL 1.1 Protocol: query and update

/me/foaf/service

SPARQL 1.1 Graph Store Protocol: bulk read and write

/me/foaf/<view>

a saved query, addressed by name

/system/accounts/me/repositories

the account’s repositories: create, list, delete

/system/accounts/me/repositories/foaf

one repository: its metadata and configuration

/me/repositories/foaf/statements

the Sesame-compatible interface, for clients which speak it

All of them are under https://dydra.com. The first two are standards – any SPARQL client can use them without knowing anything about Dydra. The third group is ours, and is where accounts, repositories, views and indices are administered.

02
authenticating

Authenticating

A token in an Authorization header, or a user name and password by HTTP basic authentication. Reading a public repository needs neither. See Getting started for where the token comes from, and the Service Access Authorization part of the reference for how access is decided once you are identified.

03
sending and receiving

Sending and receiving RDF

The Graph Store endpoint moves whole graphs. PUT replaces, POST adds, PATCH modifies, DELETE clears, GET exports:

$ curl -X POST https://dydra.com/me/foaf/service \
    -H 'Content-Type: text/turtle' \
    -H 'Content-Encoding: gzip' \
    --data-binary @foaf.ttl.gz

  • Which serialisation is stated by Content-Type going in and asked for by Accept coming out. Turtle, N-Triples, N-Quads, TriG, RDF/XML and JSON-LD are all understood. The old media type application/x-turtle is not one of them; use text/turtle.

  • Which graph is named by a graph= query argument or a Graph header. Without one, the operation applies to the default graph, or to the whole repository for DELETE.

  • How large. 128 MB per request: the compressed size for a synchronous request, the content size for an asynchronous one. Compress the body and say so; split what is bigger, or hand the service a URL and let it fetch.

  • Which revision, for a GET: a revision-id or revision-window argument reads the repository as it stood then.

A PATCH may also carry multipart/related, each part modifying the repository according to its own X-HTTP-Method-Override, which is how a single request both deletes and inserts.

04
querying

Querying

The SPARQL endpoint takes a query= parameter, or update= to write, by GET or POST. Beyond that, the parameters worth knowing:

parameter

what it does

Accept (header)

the result format: SPARQL Results JSON or XML, or an RDF serialisation

revision-uuid

evaluate against a past revision of the repository

revision-window

evaluate over a window of revisions

$variable=

bind a variable for this execution: a dynamic binding

limit, offset

bound the solution sequence returned

timeout

bound the time spent

Client-Request-ID

your own identifier, returned in the response

The full list – and there are three dozen, covering entailment, describe forms, skolemization, provenance and the rest – is the HTTP Request Parameters chapter of the reference. Two things about all of them are worth knowing here:

Where a setting may be made. A parameter may be settable in the request, in the query text as a PREFIX declaration, or in the repository, account or system configuration. A request value beats the query text, which beats configuration; among configurations, repository beats account, which beats system. A limit is the exception: a more specific setting may only lower it, never raise it.

What a cached query remembers. The processor caches compiled queries, and some parameters are compiled in: the repository’s statistics, the dataset, the entailment ruleset, the federation mode, the base IRI, and the treatment of undefined variables. Changing one of those in a later request does not change the plan already compiled.

05
namespace prefixes

Namespace prefixes

Rather than repeat the same PREFIX lines in every query, declare them once. Prefixes are part of a repository’s configuration and of an account’s, and a core set is available everywhere:

$ curl -X POST https://dydra.com/system/accounts/me/repositories/foaf \
    -H 'Content-Type: application/json' \
    -d '{"prefixes": "PREFIX ex: <http://example.org/>\n"}'

The value is ordinary SPARQL prefix syntax, one declaration per line. Account prefixes apply to every repository in the account; repository prefixes apply to that repository and override the account’s; a PREFIX in the query text overrides both. In the web interface the same settings appear on the account and repository pages.

06
repositories, views

Repositories, views and indices

The management resources create and configure things. A repository is created by POST to the account’s repository collection, deleted by DELETE, and its metadata and configuration read and written by GET and POST on the repository itself. A repository’s class – lmdb-repository, revisioned-lmdb-repository, hdt-repository, internal-view-repository – is fixed when it is created.

A view is a saved query with a name and, optionally, parameters. It is addressable like a repository resource, it can be called with bindings, and its results can be materialised into a repository of their own. A text index is created on demand when a query first addresses it, and refreshed by deleting it.

07
revisions

Revisions

Every write produces a revision, identified by the UUID of the transaction that made it. A response carries the revision it read in its ETag; a request carries the revision it wants in revision-uuid, or asks by time with Accept-Datetime. A repository also publishes a Memento timemap, so the list of states is discoverable rather than something you have to record.

This is transaction time – when the store changed. It composes with valid time, the time your data is about, which is the subject of the Temporal graphs and collated retrieval manual.

08
long operations

Long operations

An import or a large query need not be waited on. Send Accept-Asynchronous and the service replies immediately with a location to poll; the response headers Asynchronous-Location, Asynchronous-Content-Type and Asynchronous-Method say where and how. The same machinery drives streaming results over WebSocket and MQTT, for which the reference has a part of its own.

09
federation

Federation

A query may draw on more than its own repository. Internal federation runs the sub-query in the same processor against another repository here; external federation issues a request to a remote SPARQL endpoint and reads the results back into the plan; none switches it off. The mode is set by the federation parameter or in configuration.

Either direction has to be authorized. A repository lists the origins it will accept references from – authorized-client-locations – and the services it may reference – authorized-service-locations – as access control entries in the account’s system repository.

10
the public service

The public service

The free service is for evaluation, and is deliberately bounded. At the time of writing:

  • federation is disabled;

  • the default graph of the default dataset is fixed to the repository’s own default graph;

  • an undefined variable is an error, as is a non-standard vocabulary term;

  • requests are rate limited, and repositories are expected to stay modest in size – on the order of a million statements.

Dedicated servers have none of these bounds, and quality of service is provisioned per identity and class; the Quality of Service Provisioning chapter of the reference describes the mechanism. If a bound is in your way, the answer is a conversation rather than a workaround.

Note

Limits are service policy, not protocol, and policy changes. Treat the figures above as the shape of the thing and confirm the current numbers before you design around them.

11
where the details are

Where the details are

The API reference is organised by protocol, and is the specification rather than the tour:

  • SPARQL 1.1 Protocol Interface – request parameters, response formats, federation, views, asynchronous processing.

  • SPARQL 1.1 Graph Store HTTP Protocol – the service endpoint, method by method, with its headers.

  • Revisioning Interface – revision designators, windows, and the metadata.

  • Service Access Authorization – identification, access modes, access control graphs.

  • Administrative Resources – accounts, repositories, views, indices, and quality of service.

  • The Glossary names every request property in one place.
