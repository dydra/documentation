Chapter — Temporal graphs & collated retrieval

Query time, one sample at a time.

Dydra can index the valid time your data carries and retrieve a whole entity in one pass. This chapter shows how to prepare a repository, declare the temporal property, shape and load a dataset, and write time-windowed collated queries — with a worked example end to end.

01
the idea

What this capability is

A great deal of graph data is a series of samples: an observation, a reading, a tick, an event — each a subject with a small cluster of properties, and one of those properties a timestamp. Two questions dominate:

By time

“Everything that happened between t₁ and t₂.” A window on the valid-time axis.

By entity

“For this sample, all of its properties together” — the star, returned as one row rather than reassembled by the client.

Both at once

“Every sample in the window, with its whole star.” The pattern this capability is built to serve.

You do not change your data model to use it. Valid time stays an ordinary typed literal — an xsd:dateTime object on one of your predicates. You simply tell the repository which predicate carries valid time; Dydra maintains a time-ordered index over it and the query planner uses that index automatically when your query bounds that value.

02
prepare

Prepare the repository

Step 1 — create a temporal repository

Create the repository with the temporal storage class. This provisions the time-ordered index alongside the ordinary quad indices.

;; create a repository that maintains a valid-time index
(create-repository "acme/ticks"
                   :class 'temporal-value-lmdb-repository)

Step 2 — declare the temporal predicate

Tell the repository which predicate’s object is the valid time. This is recorded in the repository’s temporal-properties metadata; only quads on a declared predicate are added to the time-ordered index. You may declare more than one.

;; the object of ex:timestamp is this repository's valid time
(declare-temporal-predicates "acme/ticks"
    '("http://example.org/timestamp"))

Two time axes. The temporal index is valid time — the time your facts are about. It composes with Dydra’s existing transaction time (repository revisions): query a past revision to ask “as the graph stood then,” bound the temporal value to ask “about that period,” or do both together.

03
the data

Shape & load the dataset

Shape

Model each sample as one subject. Give it its properties as a star, and make the valid-time property a typed xsd:dateTime literal — the type is what lets the index decode and order it. Numeric and string properties are ordinary literals.

# one sample = one subject with a star of properties (N-Triples)
<http://example.org/s42> <http://example.org/timestamp> "2021-01-08T14:30:00Z"^^<http://www.w3.org/2001/XMLSchema#dateTime> .
<http://example.org/s42> <http://example.org/symbol>    "AAPL" .
<http://example.org/s42> <http://example.org/open>      "134"^^<http://www.w3.org/2001/XMLSchema#integer> .
<http://example.org/s42> <http://example.org/close>     "138"^^<http://www.w3.org/2001/XMLSchema#integer> .

Tip. Loading in time order (samples appended as time advances) lets the merge retrieval run its fastest path. Out-of-order data still returns correct results — the index simply repositions as needed.

Load

Load the file through the ordinary import path. Declared temporal predicates are indexed automatically as the quads are written — no separate indexing step.

;; stream an N-Triples/N-Quads file into the repository
(import-nquads "acme/ticks" #p"/data/ticks.nt")

Declare the temporal predicate before loading so every quad is indexed as it arrives. If you declare it after loading, reload to re-index the affected predicate.

04
the queries

Write the queries

You write ordinary SPARQL. When a query constrains a declared temporal predicate’s object to a range, the planner routes the scan through the time-ordered index for you.

A time window

PREFIX ex:  <http://example.org/>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
SELECT ?s ?p ?o WHERE {
  ?s ?p ?o .
  ?s ex:timestamp ?t .
  FILTER(?t >= "2021-01-08T00:00:00Z"^^xsd:dateTime &&
         ?t <  "2021-01-24T00:00:00Z"^^xsd:dateTime)
}

A collated star

SELECT ?s ?symbol ?open ?close ?t WHERE {
  ?s ex:symbol ?symbol ; ex:open ?open ; ex:close ?close ; ex:timestamp ?t .
}

The combination — a window of whole samples

SELECT ?s ?symbol ?open ?close ?t WHERE {
  ?s ex:symbol ?symbol ; ex:open ?open ; ex:close ?close ; ex:timestamp ?t .
  FILTER(?t >= "2021-01-08T00:00:00Z"^^xsd:dateTime &&
         ?t <  "2021-01-24T00:00:00Z"^^xsd:dateTime)
}

Bound the window with a typed xsd:dateTime on both sides (>= … && … <) so the planner can turn it into an index range. An open-ended or untyped comparison cannot be turned into a range and will fall back to a filter over the graph.

05
worked

A worked example — equity ticks

An end-to-end pass: a repository of price ticks, one sample per tick, four properties each (symbol, open, close, and a timestamp valid-time value).

1 · Create & declare

(create-repository "acme/ticks" :class 'temporal-value-lmdb-repository)
(declare-temporal-predicates "acme/ticks" '("http://example.org/timestamp"))

2 · Load

(import-nquads "acme/ticks" #p"/data/ticks.nt")   ; ticks in time order

3 · Ask — every whole tick in a two-week window

PREFIX ex:  <http://example.org/>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
SELECT ?symbol ?open ?close ?t WHERE {
  ?s ex:symbol ?symbol ; ex:open ?open ; ex:close ?close ; ex:timestamp ?t .
  FILTER(?t >= "2021-01-08T00:00:00Z"^^xsd:dateTime &&
         ?t <  "2021-01-24T00:00:00Z"^^xsd:dateTime)
}

5 · Narrow it — one symbol in the window

SELECT ?open ?close ?t WHERE {
  ?s ex:symbol "AAPL" ; ex:open ?open ; ex:close ?close ; ex:timestamp ?t .
  FILTER(?t >= "2021-01-08T00:00:00Z"^^xsd:dateTime &&
         ?t <  "2021-01-24T00:00:00Z"^^xsd:dateTime)
}

With a single, selective constant ("AAPL"), the planner drives the query from that constant instead of the window — the right choice when one symbol is far more selective than the time range.

06
the fast path

Getting the fast path

  • Declare before loading. The index is built as quads are written; a predicate declared after the fact needs a reload to re-index.
  • Type the time value. Only a typed xsd:dateTime object can be decoded and ordered. Bound it on both ends to form a range.
  • Load in time order where you can — it keeps the merge on its fastest, reposition-free path. Out-of-order data is still correct, only a little slower to scan.
  • Let selectivity choose the shape. A window over many samples is served best by the time index. A single highly-selective constant (one symbol, one id) is served best by driving from that constant. A set of several values (a disjunction) is served best by the window scan — so prefer the time bound when you are matching more than one value.
